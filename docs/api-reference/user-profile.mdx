# User Profile

View and update your profile information.

## Get Current User

Retrieve the profile of the currently authenticated user.

**Endpoint:** `GET /api/v1/account/user/me`

<Note>
  This endpoint requires JWT authentication. API keys are not supported.
</Note>

<RequestExample>
```bash cURL
curl http://localhost:8080/api/v1/account/user/me \
  -H "Authorization: Bearer <your-jwt-token>"
```
</RequestExample>

<ResponseExample>
```json 200 OK
{
  "userId": "abc123-def456-ghi789",
  "username": "myusername",
  "email": "user@example.com",
  "role": "user",
  "createdAt": "2024-01-15T10:30:00Z",
  "email_verified": true,
  "verification_required": true
}
```

```json 401 Unauthorized
{
  "error": "Unauthorized"
}
```

</ResponseExample>

`email_verified` describes proof of the current address. `verification_required` indicates whether verification is enforced for this account. Existing accounts retain access with both fields initially `false`. `pending_email` is present only while an address change awaits confirmation. These fields also appear in login and profile-update user responses.

`role` is `user` or `admin`, read from current platform membership. It appears in this profile response and the successful **200** profile-update response, but is not added to the login response. Use it to show the appropriate navigation; administrator endpoints still check membership on every request. Signup and profile updates cannot grant a role. Profile reads use `Cache-Control: no-store` and `Vary: Authorization`.

For resource counts, use the [account summary](/api-reference/account-summary).

## Update Current User

Update the profile of the currently authenticated user.

**Endpoint:** `PUT /api/v1/account/user/me`

<ParamField body="username" type="string">
  New username (minimum 6 characters)
</ParamField>

<ParamField body="email" type="string">
  New plain ASCII mailbox address (maximum 254 bytes).
</ParamField>

<ParamField body="current_password" type="string">
  Required for changing your address when email verification is enabled.
</ParamField>

<Note>
  With email verification enabled, submit username updates and email changes
  separately. Email changes require your current password and confirmation of
  the new mailbox.
</Note>

<RequestExample>
```bash cURL (Update username)
curl -X PUT http://localhost:8080/api/v1/account/user/me \
  -H "Authorization: Bearer <your-jwt-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "newusername"
  }'
```

```bash cURL (Update email)
curl -X PUT http://localhost:8080/api/v1/account/user/me \
  -H "Authorization: Bearer <your-jwt-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "newemail@example.com",
    "current_password": "<your-current-password>"
  }'
```

</RequestExample>

<ResponseExample>
```json 200 OK
{
  "message": "Profile updated successfully",
  "user": {
    "userId": "abc123-def456-ghi789",
    "username": "newusername",
    "email": "user@example.com",
    "role": "user",
    "createdAt": "2024-01-15T10:30:00Z",
    "email_verified": true,
    "verification_required": true
  }
}
```

```json 202 Accepted (Email change)
{
  "message": "Confirm the link sent to your new address. Your current email remains active.",
  "pending_email": "newemail@example.com"
}
```

```json 400 Bad Request
{
  "error": "No fields to update. Provide 'username' or 'email'."
}
```

</ResponseExample>

With verification enabled, Nebula notifies the current address and sends a confirmation link to the new address. The current email and JWT sessions remain active until the link is confirmed using [POST /auth/verify-email](/api-reference/authentication#verify-email). Confirmation changes the address atomically and revokes all previous JWT sessions. Sign in again with the new address; database API keys remain valid.

Missing or incorrect passwords return `401` with `code: "reauthentication_required"`. A request combining an email change with a username update returns `400` with `code: "invalid_email_change"`. Delivery failures return `503` with `code: "verification_delivery_unconfirmed"`; no address change is applied. Account send limits return `429` with `code: "verification_rate_limited"` and `Retry-After` in seconds until retry is allowed. The same 60-second cooldown and five-per-hour budget apply across signup verification, resends, email changes and password-recovery delivery.

A completed password reset cancels pending email-change links and revokes prior JWT sessions. An email change whose password reauthentication predates that reset cannot issue a fresh link.

Only the most recent pending target can be confirmed. If that delivery fails, an earlier successfully delivered pending request is retained. Confirmation of an address already claimed by another account returns `409` with `code: "email_conflict"` and preserves the current email.

When verification is disabled, legacy accounts keep the existing immediate email-update behavior and may update both fields together. Accounts already subject to verification cannot bypass confirmation by disabling SMTP; their email changes return `503` with `code: "verification_disabled"` until delivery is configured again.


## Profile photos and onboarding

Login, current-profile and successful profile-update responses include:

| Field | Meaning |
| --- | --- |
| `avatar_url` | GitHub HTTPS image URL, relative `/avatars/<asset-id>` URL, or an empty string |
| `avatar_source` | `github`, `upload`, `none` (explicit removal), or empty (not configured) |
| `onboarding_completed` | Persisted completion, including choosing to skip |

Resolve relative avatar URLs against the backend origin, not the frontend origin. GitHub sign-in and connection import the provider's avatar when available. Later sign-ins refresh that default but preserve an uploaded photo or explicit removal. Missing or invalid provider images do not prevent authentication. Images that fail to load should fall back to initials.

### Upload a photo

`POST /api/v1/account/user/me/avatar` requires an owner JWT and multipart form data containing exactly one file named `avatar`.

```bash
curl -X POST http://localhost:8080/api/v1/account/user/me/avatar \
  -H "Authorization: Bearer <your-jwt-token>" \
  -F "avatar=@photo.png"
```

JPEG, PNG and WebP images are accepted up to **2 MiB**, **4096 pixels per side**, and **8,388,608 total pixels**. The server checks decoded content independently of filenames or supplied MIME types, center-crops to 256 × 256, and encodes a JPEG without original metadata. Transparency is flattened onto white. The image is stored with account metadata and deleted with the account. A successful upload returns the current profile directly with HTTP 200 and completes onboarding.

Profile images are public through `GET /avatars/<asset-id>`. Asset IDs are random and do not expose user IDs or file paths. Responses contain only normalized JPEG bytes, use `nosniff` and `no-store`, and do not reveal account details. Replacing or removing a photo makes the old asset URL return 404. Downloaded copies cannot be recalled.

Invalid content returns 400 (`invalid_avatar`), oversized payloads return 413 (`avatar_too_large`), invalid multipart content type returns 415, and a full image-processing budget returns 503 (`avatar_busy`). Rejected uploads leave the current photo unchanged. Writes are not automatically retried; check the current profile after an uncertain response.

### Remove a photo

`DELETE /api/v1/account/user/me/avatar` requires an owner JWT, accepts no payload, and returns the current profile directly with HTTP 200. It clears stored image bytes and records an explicit opt-out from future automatic GitHub imports. Repeating removal is safe. Initials can be shown instead.

### Complete or skip onboarding

`POST /api/v1/account/user/me/onboarding` requires an owner JWT, accepts no payload, and returns the current profile directly with HTTP 200. It sets `onboarding_completed` to `true` without changing the avatar. Repeating it is safe. New and existing accounts without recorded completion begin with `false`; the frontend offers photo setup after sign-in and allows skipping. Avatar setup never requires SMTP.

Database API keys cannot upload/remove account photos or complete onboarding. Older servers omit these profile fields and do not expose the new routes.
