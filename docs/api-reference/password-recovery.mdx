# Password recovery

Password recovery is opt-in and independent of signup email verification. Deploy the compatible frontend and configure authenticated SMTP before setting `PASSWORD_RESET_ENABLED=true`. Both routes are public and require no JWT or database API key.

## Request a reset link

**Endpoint:** `POST /auth/forgot-password`

```bash
curl -X POST http://localhost:8080/auth/forgot-password \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com"}'
```

Valid known, unknown, suspended and rate-suppressed account addresses receive the same `202 Accepted` acknowledgement while worker capacity is available:

```json
{
  "message": "If this address is eligible, a password reset email will be sent."
}
```

The response does not confirm account existence, SMTP acceptance or inbox delivery. Lookup and delivery run asynchronously in at most four concurrent recovery workers. These workers are not a durable queue; a process restart can interrupt delivery. Request another link after the cooldown if needed. Requesting recovery never changes a password, signs out a user or unlocks an account.

The message links to `APP_PUBLIC_URL/reset-password#token=...`. The origin comes from validated server configuration, never the request's Host header. The frontend removes the fragment before analytics mount, retains the token only in memory and submits it only with the new password. Reloading the cleaned page requires reopening the email link.

## Replace the password

**Endpoint:** `POST /auth/reset-password`

```bash
curl -X POST http://localhost:8080/auth/reset-password \
  -H 'Content-Type: application/json' \
  -d '{"token":"<token-from-email>","password":"a-new-password"}'
```

The password must contain at least eight Unicode characters and at most 72 UTF-8 bytes, matching signup. Clients should ask users to enter it twice. The backend accepts only `token` and `password`; do not send account IDs, email addresses or a full URL.

A successful reset returns `200 OK`:

```json
{ "message": "Password reset successfully. Sign in with your new password." }
```

The credential change, session-version increment, removal of all reset tokens and removal of pending email-verification/change links commit in one metadata transaction. Competing submissions can succeed only once. Reset links expire after 30 minutes by default, are bound to the account's current email and session version, and are stored only as SHA-256 hashes of random 256-bit tokens. Previously delivered reset links remain usable until expiry or a successful reset; a failed delivery discards only its own token.

Resetting a password does not sign in the user or mark an email verified. Suspended accounts cannot reset, and accounts requiring email verification still need to verify before login. Tenant databases, API keys, administrator membership and verification requirements remain unchanged. Rotate database API keys separately if they may have been compromised.

Existing JWTs are rejected after a reset. The frontend clears its local session after confirmed success; SDK callers should clear any stored JWT themselves and sign in again. A password-change notification is attempted asynchronously without including the password. Notification failure cannot undo a committed reset and does not change its successful HTTP response.

## Errors and retry behavior

| HTTP status | Code                           | Client action                                                                      |
| ----------- | ------------------------------ | ---------------------------------------------------------------------------------- |
| `400`       | `invalid_email`                | Enter a plain ASCII mailbox, at most 254 bytes                                     |
| `400`       | `invalid_password`             | Follow the signup password limits                                                  |
| `400`       | `invalid_password_reset_token` | Request a new link; includes expired, used, superseded or suspended-account tokens |
| `400`       | `invalid_auth_request`         | Submit one JSON object with only documented fields                                 |
| `413`       | `request_too_large`            | Keep the complete body within 4 KiB                                                |
| `415`       | `unsupported_media_type`       | Send `application/json`                                                            |
| `429`       | `password_reset_rate_limited`  | Respect `Retry-After`; public IP budget exceeded                                   |
| `503`       | `password_reset_disabled`      | Operator must enable and configure recovery                                        |
| `503`       | `password_reset_busy`          | Worker capacity is occupied; wait and request again                                |
| `503`       | `password_reset_unavailable`   | Read current state before retrying a reset                                         |
| `408`       | `request_timeout`              | Completion may be uncertain; try signing in before requesting another link         |

All recovery responses use `Cache-Control: no-store`. With recovery enabled, both routes share a persistent budget of 10 requests per client IP per 15 minutes with enabled signup/resend routes. Limit responses use `Retry-After: 900`. Verification and recovery mail share the existing per-account 60-second cooldown and five-request hourly budget. Account-specific suppression remains hidden behind the generic request acknowledgement. Global IP limits also apply.

A lost connection, timeout or server error during reset can leave the result uncertain. Never retry the write automatically. Try signing in with the new password, or request a new link after the cooldown. A used-token error after an uncertain attempt does not prove that the password stayed unchanged.

## Local testing and rollout

Run `./scripts/dev-email.sh` from the backend repository, or `./dev.sh --email` from the three-repository workspace. The local runner enables recovery and verification with an isolated account database and an authenticated TLS Mailpit inbox at `http://localhost:8025`. Mail is captured locally; production SMTP and normal local accounts are untouched.

Deploy in this order: backend routes, frontend `/forgot-password` and `/reset-password` pages, then enable recovery in the backend environment. See [configuration](/guides/configuration) for SMTP and token-lifetime settings. Disabling recovery disables both endpoints, including consumption of existing links. Preserve the metadata database during deployment and rollback.
