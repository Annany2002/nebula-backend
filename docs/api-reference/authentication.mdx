# Authentication

Register users, confirm email addresses and obtain JWT sessions for API access. For forgotten passwords, see [password recovery](/api-reference/password-recovery). For optional provider-based sign-in, see [GitHub sign-in](/api-reference/github-sign-in).

## Sign Up

Create a new user account.

<ParamField body="email" type="string" required>
  User's email address (must be valid email format)
</ParamField>

<ParamField body="username" type="string" required>
  Username (minimum 6 characters)
</ParamField>

<ParamField body="password" type="string" required>
  Password (minimum 8 characters, maximum 72 UTF-8 bytes)
</ParamField>

<RequestExample>
```bash cURL
curl -X POST http://localhost:8080/auth/signup \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "username": "myusername",
    "password": "securepassword123"
  }'
```
</RequestExample>

<ResponseExample>
```json 201 Created
{
  "message": "User registered successfully",
  "user_id": "user-uuid"
}
```

```json 409 Conflict
{
  "error": "Email already exists"
}
```

</ResponseExample>

---

With `EMAIL_VERIFICATION_ENABLED=true`, signup creates a restricted account and attempts SMTP delivery:

```json
{
  "user_id": "user-uuid",
  "message": "Account created. Verify your email before signing in.",
  "verification_required": true,
  "verification_delivery": "sent"
}
```

`verification_delivery` is `sent` when the SMTP server accepts the message, or `unconfirmed` when delivery cannot be confirmed. Neither value guarantees inbox delivery. On failure the account remains restricted; request another email after the send cooldown. Signup never returns a verification token or a login session.

## Login

Authenticate and receive a JWT token.

<ParamField body="email" type="string" required>
  User's email address
</ParamField>

<ParamField body="password" type="string" required>
  User's password
</ParamField>

<RequestExample>
```bash cURL
curl -X POST http://localhost:8080/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "securepassword123"
  }'
```
</RequestExample>

<ResponseExample>
```json 200 OK
{
  "message": "Logged in successfully",
  "user": {
    "userId": "user-uuid",
    "email": "user@example.com",
    "username": "myusername",
    "createdAt": "2026-10-02T12:00:00Z",
    "email_verified": true,
    "verification_required": true
  },
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

```json 401 Unauthorized
{
  "error": "Invalid credentials"
}
```

</ResponseExample>

---

Correct credentials for an account that still requires verification return `403` with `code: "email_verification_required"`. Protected endpoints also enforce this requirement for JWT and API-key authentication, even if a token or key already exists. Existing accounts retain access without being marked verified; their profiles initially report `email_verified: false` and `verification_required: false`.

## Verify Email

**Endpoint:** `POST /auth/verify-email` (public)

Send the token from the email link in a JSON body:

```bash
curl -X POST http://localhost:8080/auth/verify-email \
  -H 'Content-Type: application/json' \
  -d '{"token":"<token-from-email>"}'
```

Successful verification returns `200`:

```json
{ "message": "Email verified successfully. Sign in to continue." }
```

Tokens are single-use and expire after 30 minutes by default. Malformed, expired, previously used, and superseded email-change tokens return `400` with `code: "invalid_verification_token"`. An email-change target claimed by another account returns `409` with `code: "email_conflict"`; the current email remains unchanged. Storage failures return `500` with `code: "verification_unavailable"`.

The endpoint issues no JWT. Sign in after confirmation. It can finish previously issued tokens even if email delivery is subsequently disabled.

<Note>
  Links use `APP_PUBLIC_URL/verify-email#token=...`. The frontend must read and
  remove the fragment, then submit the token in a POST body. Do not move tokens
  into URL queries, logs, or analytics. Deploy this frontend flow before
  enabling verification.
</Note>

## Resend Verification

**Endpoint:** `POST /auth/resend-verification` (public)

```bash
curl -X POST http://localhost:8080/auth/resend-verification \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com"}'
```

Well-formed known and unknown addresses receive the same `202` response when worker capacity is available:

```json
{ "message": "If this address is eligible, a verification email will be sent." }
```

Delivery is attempted asynchronously only for eligible unverified addresses. This acknowledgement does not guarantee delivery. Work is bounded to four concurrent requests and is not a durable mail queue; request again if a restart interrupts delivery. Verified and unknown addresses receive no email.

When verification delivery is disabled, the endpoint returns `503` with `code: "verification_disabled"`. When all delivery workers are occupied, it returns `503` with `code: "verification_busy"`, regardless of account existence.

## Limits and Address Policy

With verification enabled, signup and resend share a persistent limit of 10 requests per client IP in 15 minutes. Enabled password-recovery routes use the same budget. Verification and recovery delivery share the account send budget below. Exceeding it returns `429` and `Retry-After: 900`. Account email delivery has a 60-second cooldown and a maximum of five requests per hour; both survive server restarts. Public resend responses do not expose account-specific limits. Existing global IP limits also apply.

Verification and resend require `application/json`, accept one JSON object with no unknown fields, and limit request bodies to 4 KiB. Unsupported media types return `415`, oversized bodies return `413`, and invalid payloads return `400`.

Addresses must be plain ASCII mailboxes, at most 254 bytes, without display names or header line breaks. Existing exact, case-sensitive address comparisons are retained. No provider-specific dot/plus normalization or disposable-address filtering is applied.

## Using the Token

User responses never contain passwords or password hashes. Sign up and verification do not issue a token; log in after completing any required email confirmation.

Include the JWT token in subsequent API requests:

```bash
curl http://localhost:8080/api/v1/databases \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

<Note>
  JWT tokens expire based on the `JWT_EXPIRATION_HOURS` configuration (default:
  24 hours).
</Note>
